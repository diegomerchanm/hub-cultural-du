# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**Hub Cultural DU** is a data pipeline for mapping and analyzing cultural networks (originally Colombian diaspora, now general cultural accounts in France too) on Instagram. It scrapes Instagram profiles via Apify, ingests data into a Neo4j graph database, and combines automated graph analysis with hand-curated categorization to score cultural relevance and detect communities.

**Pipeline Phases:**
1. **Extraction** — `1_harvest_ig_profiles.py` / `1_harvest_ig_posts.py` / `extract_profiles.py` → scrape Instagram via Apify → `data_raw/*.json`. Target usernames come either from `config/seeds_*.json` (`--seeds`, recommended) or, for `1_harvest_ig_posts.py` only, from `data_processed/account_scores.csv` as a legacy fallback (see `old/1_harvest_account_classifier.py`).
2. **Ingestion** — `2_build_graph.py` → loads JSON files into Neo4j Aura
3. **Analysis** — `3_analyze_network.py` → local graph metrics (igraph/leidenalg — no GDS plugin needed, works on standard AuraDB). `old/run_gds_algorithms.py` is archived: it depends on the Neo4j GDS plugin, which standard AuraDB doesn't include, so it never runs successfully in this project's setup.
4. **Manual categorization** (now the primary trust signal, not just a complement — see below) — `load_manual_account_categorization.py` → uploads hand-curated fields (art type, institution type, cultural identity, geographic zone, pricing/free-events info, verified follower counts) from a curated spreadsheet onto `:Account` nodes by `username`.
5. **Events** — `4_enrich_events_extract.py` (embeddings + NLI filter, LLM classifies/enriches/gates → `:Event` nodes with inline dedup — see Key Architecture Notes) → `4_enrich_events_resolve.py` (standalone dedup pass for existing `:Event` nodes)
6. **Geo** — `4_enrich_locations.py` → Nominatim geocoding + `:LOCATED_IN` hierarchy
7. **Cleanup** — `cleanup_legacy_accounts.py` → one-off (repeatable) deletion of `:Account` nodes never touched by manual curation, plus everything that depends exclusively on them (see below)
8. **Staging review** — `review_events.py` (Streamlit) → Diego reviews every newly-created `:Event` (tagged `:PendingReview` at creation by `4_enrich_events_extract.py`) before it reaches the live site: aprobar (removes `:PendingReview`), editar (inline form, saves fields), or rechazar (soft — adds `:Rejected`, never a real delete). `5_export_dashboard_data.py` and `export_events_excel.py` exclude both `:Rejected` and `:PendingReview` by default.
9. **Publish** — `5_export_dashboard_data.py` writes `site/data.json`, but that alone does NOT update the live site: `site/` deploys to Cloudflare Workers via `wrangler.jsonc` (Workers Assets, static files served from `site/`), a separate manual step (`cd site && npx wrangler deploy`) with no automatic trigger from `git push` or from running the export script. Forgetting this step is the most likely reason newly-approved events don't show up on the live site even after export + `git push` both succeeded (confirmed 2026-08-25 — DD-053).

**Folder conventions:** `old/` holds scripts that are superseded or don't work in this project's actual environment (kept for reference, not run). `testing/` holds verification/diagnostic scripts (`verify_events_extraction.py`, `check_geotag_coverage.py`, `test.py`, `plot_eventscore_boxplot.py`) that are still useful for QA but aren't part of the main pipeline flow.

python 3_analyze_network.py run-all         # Phase 3: local analysis (igraph/leidenalg) — no GDS or port 7687

python load_manual_account_categorization.py --dry-run   # Phase 4: preview curated-spreadsheet upload
python load_manual_account_categorization.py             #   write it to Neo4j (idempotent, safe to re-run)
python seal_legacy_batch.py --dry-run       # One-time: preview which nodes have no ingestion timestamp yet
python seal_legacy_batch.py                 #   tag them legacyBatch=true before the next harvest run
python 4_enrich_events_extract.py           # Phase 5-A: detect events → :Event nodes

# Key options

## Graph Data Model

**Nodes:** `:Account` (`:Public` | `:Private`, optionally `:Political`), `:Post`, `:Hashtag`, `:Location`, `:Track`, `:Comment`, `:IgtvVideo`, `:Event`, `:City`, `:Country`, `:Arrondissement`

**Relationships (original):** `PUBLISHED`, `HAS_HASHTAG`, `MENTIONS`, `TAGS_USER`, `COAUTHORED_BY`, `TAGGED_AT`, `USES_MUSIC`, `WROTE`, `ON`, `LOCATED_AT`, `RELATED_TO`

**Relationships (NLP/Geo):** `MENTIONS_EVENT`, `ORGANIZED`, `PARTICIPATED_IN`, `SUPPORTED`, `LOCATED_IN`

## Key Architecture Notes

- **Incremental processing:** `extract_profiles.py` queries Neo4j for accounts not yet scraped, making re-runs idempotent.
- **Cost control:** Apify usage is tracked in `.apify_cost_log.json` (gitignored). Always check estimated cost before running large extractions.
- **Political filtering (archived):** 13 political accounts were hardcoded in `old/run_gds_algorithms.py` and down-weighted in the Cultural Relevance Score. Since that script is archived (see below), the `:Political` label is no longer being freshly applied to new accounts — this filtering is currently dormant, not something any active script maintains.
- **Cultural Relevance Score (archived):** lived entirely in `old/run_gds_algorithms.py` — percentile-rank blend of PageRank/Degree/Betweenness × political penalty, `followersCount` reported separately as `popularityScore`. Archived because it depends on the Neo4j GDS plugin, which standard AuraDB doesn't include (it never ran successfully in this project's actual environment). `3_analyze_network.py` is the live alternative for relevance/centrality signal — check its actual output property names in `data_processed/*.csv` before assuming they match the old GDS-era names.
- **Local analysis (3_analyze_network.py):** offline alternative to GDS (port 7687 is often blocked and standard AuraDB does not include GDS) — this is the live, working phase-3 script. Exports to `data_processed/*.csv`, runs igraph/leidenalg (exact PageRank and betweenness, Leiden γ=0.5/1.0/1.5 with seed=42, WCC, k-core, participation coefficient, E-I index by actor type) and writes back with `UNWIND` in batches. **Multiplex** network: social layer (MENTIONS/TAGS_USER/COAUTHORED_BY projected author→post→target, since in the raw graph they originate from the Post) separate from the algorithmic layer (RELATED_TO, `Algo` suffix). Actor typology can be curated in `data_processed/actor_types.csv`.
- **Manual categorization:** `load_manual_account_categorization.py` uploads a hand-curated spreadsheet (art type, institution type, event frequency, parent institution, content type, verified follower count, free-events/pricing info, cultural identity, geographic zone, photo permission — see the script's `COLUMN_MAP`) onto `:Account` nodes via `MERGE` by `username`. Property names (`artType`, `culturalIdentity`, `geoZone`, `manualFollowersCount`, etc.) are deliberately distinct from what `2_build_graph.py` writes, so re-running either script never clobbers the other's data. Idempotent, safe to re-run whenever the source spreadsheet changes.
- **Photo permission gate (2026-08-27, DD-060 — legal/reputational risk mitigation, not a technical fix):** column 14 of the curated spreadsheet asks explicitly whether the account authorized displaying their photos on the site. `_is_yes()` in `load_manual_account_categorization.py` normalizes free text to `True`/`False`/`None` (`None` = not asked yet), written to `:Account.photoPermission`. `4_enrich_events_extract.py` inherits it onto `:Event.photoPermission` at creation time, same no-LLM-cost pattern as `artType`/`geoZone`/etc. — **fails closed**: both `False` and `None` are treated identically by the frontend (no explicit "yes" → no real photo shown), so accounts nobody has asked yet default to the safe state. `site/app.js`'s `hasPhotoPermission(ev)` gates every place `ev.imageUrl` would render a real photo (cards, hero, detail panel) — without permission, cards/hero fall back to the existing color+icon placeholder, and the detail panel falls back to Instagram's own official oEmbed/`<blockquote class="instagram-media">` embed (`detailMediaHtml()`) instead of hosting a copy of the image, since that renders live from Instagram's own CDN with the rightsholder's own sanctioned mechanism rather than a scraped copy.
- **Human curation as the trust signal (methodology shift):** the project moved away from trusting the old automated selection criterion (`old/1_harvest_account_classifier.py`'s scoring) — in practice, well under 10% of accounts it selected turned out to be culturally valuable. `manualDataCuratedAt IS NOT NULL` (set only by `load_manual_account_categorization.py`) is now the operative signal for "this account is worth keeping," replacing the old scoring-based selection. Note this is *not* the same thing as `legacyBatch` — that property never actually ended up tagging any real node in practice (by the time `seal_legacy_batch.py` was run, every node already had some other date field), so it's dormant, not a usable filter.
- **Cleanup:** `cleanup_legacy_accounts.py` deletes `:Account` nodes with no `manualDataCuratedAt`, cascading to their `:Post`/`:IgtvVideo` (via `PUBLISHED`) and `:Comment` (via `WROTE`) — in that order, since deleting the account first would remove the very relationship needed to find what belonged to it — then sweeps `:Hashtag`/`:Location`/`:Track`/`:Event`/`:Arrondissement`/`:City`/`:Country`/`:Comment` nodes left with zero relationships (repeated passes, since removing one orphan can orphan its parent, e.g. `Location → Arrondissement`). **Exception:** before deleting, it tags (not deletes) any account reached via `RELATED_TO` from a curated account with `discoveredViaCuratedAccount = true` / `candidateReviewStatus = 'pending'` — `2_build_graph.py` creates one `:Account` per Instagram `relatedProfiles` suggestion on every scrape, so some "uncurated" accounts are fresh discoveries surfaced through a trusted seed, not old junk; these survive as a to-review pool instead of being deleted. Runs inside one transaction with `ROLLBACK` on `--dry-run` (or if the confirmation prompt is declined), so dry-run counts are exact, not estimated. Not run automatically by CI — deliberately manual given it's irreversible. `testing/verify_cleanup.py` checks post-run state (label counts, that no account without `manualDataCuratedAt` survived outside the candidate pool, no orphans left, candidate pool breakdown by `candidateReviewStatus`).
- **raw data:** `data_raw/` is gitignored; JSON files are named `profile_<username>.json`.
- **NLP scripts are idempotent:** each checks for a `NULL` sentinel property before processing (`eventExtracted`, `lat`). The bio/caption language+NER+keywords enrichment (`old/4_enrich_nodes_nlp.py`) is archived — nothing downstream in the active pipeline reads `bioLanguage`/`captionLanguage`/`bioEntities`/`captionEntities`/`bioKeywords`/`captionKeywords`/`bioEmbedding`/`captionEmbedding`, so it was cut rather than kept as dead weight. Revive from `old/` if a future feature (language-based filtering, topic clustering) actually needs it.
- **Ingestion provenance:** `2_build_graph.py` sets `firstSeenAt` (`ON CREATE`) and `lastUpdatedAt` (always) on every node it touches (`Account`, `Post`, `Hashtag`, `Location`, `Track`, `Comment`, `IgtvVideo`). Nodes created before this was added have neither property — `seal_legacy_batch.py` exists to tag that pre-existing state with `legacyBatch = true` / `legacyBatchDate`, though in this project's actual data every node ended up with some other date field already, so it never had anything to seal. The practical mechanism for cleaning up old/irrelevant accounts turned out to be `cleanup_legacy_accounts.py` (see below), keyed on `manualDataCuratedAt` rather than `legacyBatch`.
- **NLP models:** spaCy lazy-loads per language (`es_core_news_lg` / `en_core_web_sm` / `fr_core_news_lg`). Entities stored as `"TYPE:texto"` strings (e.g. `"ORG:Ministerio de Cultura"`). Embeddings via `paraphrase-multilingual-MiniLM-L12-v2` stored as float lists, compatible with Neo4j vector indexes.
- **Event extraction flow (rewritten 2026-08, see `data_processed/eval_100_report.md` for the eval that drove this):** 3 layers, not 4 — the old Capa 2b (embeddings-based multi-label typification) was removed after a 100-post human-vs-pipeline comparison showed the LLM classifies event type more accurately and without the reference-set bias described below. Capa 1 (`paraphrase-multilingual-MiniLM-L12-v2`, cosine similarity vs ~100 reference phrases) filters candidates. Capa 2a (`MoritzLaurer/multilingual-MiniLMv2-L6-mnli-xnli`, binary NLI) decides if it's event-like at all — the hypothesis is now picked in the caption's own detected language (`DET_HYPOTHESES` es/en/fr) since a fixed-Spanish hypothesis was shown to crater scores for English/French captions regardless of content. Capa 3 (LLM — Ollama/Groq/Google/DeepSeek/Cerebras, `LLM_PROVIDER` env var; cloud providers fall back automatically groq → google → cerebras → deepseek when one is exhausted or fails, see DD-033 update 8 and DD-050 for the reorder) now also **tipifica el evento** (`type`, same 16-label taxonomy `_LABEL_META` that Capa 2b used to own), gives `price_range` (replaces the old boolean `isFree`), and — the important change — **gates event creation**: if the LLM ran successfully and said the post is not a real upcoming public invitation (`is_public_invitation`/`is_upcoming`), the `:Event` node is no longer created at all (previously it was created anyway with a low score, which the eval showed explained the majority of false-positive events). `reasoning` is only requested from the LLM in `--dry-run`. Calls to Capa 3 are deduplicated by `post_id` within a run (co-published posts share one LLM call). New `:Event` nodes also inherit `artType`/`institutionType`/`culturalIdentity`/`geoZone`/`parentInstitution` directly from the publishing `:Account`'s manual curation (no LLM cost — only populated when the account has `manualDataCuratedAt`). Inline resolver still checks cosine similarity > 0.82 + location match + date ±3 days before creating vs. enriching. Event IDs are MD5 hashes of `type|raw_date|location`.
- **Bilingual event content (DD-051, DD-054):** the same Capa 3 call also generates `title_fr`/`description_fr` and, since DD-054, `art_tags_fr` (French translation of `art_tags`, aligned by position) — no extra LLM calls, just more output tokens on the call that already runs. Written to Neo4j (`titleFr`/`descriptionFr`/`eventArtTagsFr`) only in the creation branch of `upsert_event`, same as every other Capa-3 field there — never backfilled by re-running the extractor on existing events. `site/app.js` falls back to the Spanish field whenever the French one is missing (`evTitle`/`evDescription`/`themeLabel`), so old events display fine in FR mode, just without their own translation. `eventArtTagsFr` has a dedicated backfill path (`backfill_art_tags_fr.py`) precisely because its vocabulary is small and highly repeated across events — see Commands above — unlike `titleFr`/`descriptionFr`, which are one-off per event and were judged not worth backfilling.
- **Site i18n scope (DD-054):** `site/i18n.js`'s `CURRENT_LANG` toggle now also drives the fixed 11-category taxonomy, `geoZone` labels, and date month names (`categories`/`geoLabels`/`months` per language) — previously only interface chrome (menus, filters, labels) switched language, while event-derived text stayed in Spanish regardless of the toggle. The filter's internal identity (`STATE.theme`, `catWeights` persisted in visitor `localStorage`) is still the Spanish string; only the rendered label is language-aware, via `categoryLabel()`/`geoLabel()`/`themeLabel()` in `app.js`. `ev.artType` (account-level curated free text, distinct from event-level `eventArtTags`) and badge tooltips ("Puente"/"Resonando"/etc.) are known to have the same hardcoded-Spanish issue but were left untouched — out of scope of this pass.
- **Event resolver (standalone):** groups `:Event` nodes by `locationName`, compares pairs by date window then cosine similarity, merges duplicates by redirecting all relationships explicitly (no APOC). Canonical = higher `hotnessScore`.
- **Geocoding:** `4_enrich_locations.py` uses Nominatim (1.1 s/req rate limit). Paris arrondissements detected from postal code 750XX. Hierarchy: `Location -[:LOCATED_IN]-> Arrondissement -[:LOCATED_IN]-> City -[:LOCATED_IN]-> Country`. Sessions logged in `.geocoding_log.json` (gitignored).
- **Post source traceability (2026-08-24, DD-048):** `2_build_graph.py` ingests posts from two places — `posts_<username>.json` (dedicated scraper, `1_harvest_ig_posts.py`, verified `onlyPostsNewerThan` window per DD-029) and the `latestPosts` field embedded inside `profile_<username>.json` (from `1_harvest_ig_profiles.py`, no date-window guarantee at all). Both go through the same `load_posts(tx, username, posts, source)`, which now sets two accumulating booleans, `p.sourceDedicatedScraper` / `p.sourceProfileEmbed` (never downgraded to `false` once `true`, via `coalesce` — a post can carry both flags if seen through both paths over time). The two sources are also distinguishable directly in the raw JSON: the profile embed lacks `latestComments`/`musicInfo`/`firstComment`/`productType`/`inputUrl`/`originalWidth`/`originalHeight`/`ownerFullName` even for a post with identical `id`/`timestamp` in both files. `4_enrich_events_extract.py`'s candidate query defaults to `p.sourceDedicatedScraper = true` only (`--only-dedicated-scraper`, override with `--include-profile-embed`) plus a `--max-post-age-days` filter (default 20, string-compares the first 10 chars of `p.timestamp` rather than parsing `datetime()`, to tolerate malformed timestamps) — both exist so Capa 1/2/3 don't spend cost on posts with no recency guarantee.
- **HikerAPI as an Apify alternative for post scraping (2026-08-27, DD-059, exploratory — not yet adopted as default):** `1_harvest_ig_posts_hikerapi.py` targets `GET /v1/user/medias/chunk`, normalizing HikerAPI's response into the exact same `posts_<username>.json` shape `1_harvest_ig_posts.py` (Apify) already produces, so `2_build_graph.py` ingests either source with zero changes — it treats anything in `posts_<username>.json` as `source="dedicated_scraper"` regardless of which script wrote it, which is a reasonable fit here since `harvest`'s `--max-days` client-side filter gives a comparable recency guarantee to Apify's `onlyPostsNewerThan`. Known field gaps vs. Apify (documented in the script's own docstring, not fixed): no `musicInfo`/`latestComments` (would need extra paid calls per post — confirmed via grep that the live event-extraction pipeline doesn't read either field, so impact is low), and `hashtags`/`mentions` are regex-reconstructed from `caption_text` rather than pre-parsed entities. **Not calibrated against a real API call** — the sandbox this was written in has no network route to `api.hikerapi.com` (`ProxyError 403`, same class of block that already affects Neo4j from this environment), so the response-shape parsing is defensive (accepts both `[items, cursor]` and `{"items":...}`, same pattern already needed once for `/v1/user/following/chunk` in DD-049, where the public doc didn't match reality). Diego must run `calibrate` (one real call, ~$0.001) and `compare` (checks field coverage + cost against an existing Apify-scraped account, writes to `posts_hikerapi_<username>.json` without touching the Apify file) before trusting `harvest` at any real scale.
- **Static SEO pages for AI crawlers (2026-08-27, DD-067):** the interactive site (`index.html` + `app.js`) is 100% client-rendered — GPTBot/ClaudeBot/PerplexityBot don't execute JavaScript (confirmed 2026-08), so they only ever see an empty shell there, regardless of URL. `6_generate_seo_pages.py` (no Neo4j needed, reads `site/data.json` directly) generates real static HTML at `site/categoria/<slug>/index.html` for each fixed `category` (11 values, 100% populated — the only taxonomy solid enough for this yet; `geoZone`/`cityName` are still too sparse, see DD-066) with >= `--min-events` (default 3) upcoming events, each page embedding schema.org `Event` JSON-LD (`@graph`) and linking every event back into the interactive site via the `?evento=<id>` deep link (DD-063). Also writes `site/categoria/index.html` (hub), `site/sitemap.xml`, and rewrites a marked block in `site/index.html`'s footer with real `<a href>` links to each generated category page — without those static links, a JS-blind crawler has no way to discover `/categoria/*` at all. `site/robots.txt` is static (not regenerated) and points to the sitemap. Not yet chained automatically into the pipeline — run it manually after `5_export_dashboard_data.py` and before `wrangler deploy`. Country/city pages (Etapa 3) are deferred until the geo data-quality work happens.
- **Staging review (2026-08-21):** every `:Event` node created by `4_enrich_events_extract.py` is now also tagged `:PendingReview` at creation time (in the `else:` / brand-new-event branch of `upsert_event`), so new events are hidden from the live site until Diego reviews them by hand in `review_events.py` (local Streamlit app: aprobar removes `:PendingReview`; editar saves field changes inline; rechazar adds `:Rejected` and removes `:PendingReview` — this is the *only* form of "delete" in this feature, per explicit decision to never `DETACH DELETE` an event node). `5_export_dashboard_data.py`'s `EVENTS_QUERY` and `export_events_excel.py` (new `--include-pending` flag, off by default) both exclude `:PendingReview` the same way they already excluded `:Rejected`. Events that existed in Neo4j before this change have neither label and remain live, unaffected. Chosen over reviving the archived `old/dash_common.py` Dash app (already abandoned once, per `old/` convention) — Streamlit needed no new infra, no auth, no hosting, just `streamlit run review_events.py` on Diego's machine.

## Lessons for replicating this project in another city

- **Discovery-source keyword pattern (found 2026-08-20, while manually reviewing the ~7897-account candidate pool from the following/relatedProfiles expansion):** roughly 90% of candidate accounts clustered around a handful of recurring keyword stems in the username/name — `theatre`, `litterature`, `librairie`, `livre`, `impro`, `asso`, and similar terms for the relevant language/domain. Scraping every seed account's full follower/following list (the approach used this round, see `1_harvest_ig_network_hikerapi.py` and the manual console scraper referenced in `docs/decisions_es.md` DD-046) is expensive and produces a huge low-signal pool (~90% ends up discarded by manual/LLM review). If this project is ever forked for a new city, it is probably far cheaper and higher-precision to search Instagram directly by these keyword stems (localized to the target language) than to crawl full follower graphs and filter after the fact.
